# ADR-0020: Ревизии и предпросмотр

- Статус: принято
- Дата: 2026-10-31

## Контекст

Документацию правят итерациями; нужны история, откат и просмотр до публикации (docs/roadmap.md, релиз 3).

## Решение

- **Ревизии.** Каждое сохранение добавляет неизменяемую ревизию в `entry_revisions` (миграция 0004): заголовок, slug, блоки, автор, время. Одинаковое содержимое ревизию не создаёт. Хранятся бессрочно.
- **Целостность.** Каждая ревизия подписана HMAC (ключ, выведенный из `var/keys/cache.key`, вне БД) поверх MAC предыдущей. Подмена, удаление или вставка видны в истории; при нарушенной цепочке публикация и откат блокируются.
- **Публикация по требованию.** Строка `entries` — то, что на сайте. У черновика она совпадает с последней ревизией; у опубликованной записи «Сохранить изменения» только добавляет ревизию, а сайт меняется по «Опубликовать изменения» (`entries.published_revision`). Это меняет поведение «Save» из `bb91671`.
- **Откат** — новая ревизия-копия старой с пометкой «восстановлено из #n», запись `revision_restored` в журнале аудита.
- **Сравнение** — построчный LCS по заголовку, slug и тексту блоков; больше 600 строк на сторону — без сравнения, обе версии целиком.
- **Предпросмотр** — `/admin/preview/{token}` под RequireStaff. Токен — HMAC, 15 минут, привязан к ревизии и запросившему сотруднику. Ответ: `X-Robots-Tag: noindex`, `Cache-Control: no-store`, `Referrer-Policy: no-referrer` (SecurityHeaders позволяет только ужесточить Referrer-Policy).

## Последствия

- Рубрики, теги и место в меню не версионируются и применяются сразу.
- Записи до релиза получают первую ревизию при первом обращении (ensureBaseline), без подписи задним числом.
- Одновременное сохранение одной записи двумя людьми: второе падает на UNIQUE (entry_id, seq) — без потери данных, но с ошибкой 500.
- Abuser Stories: revision-tamper, revision-snooping, unpublished-change-leak, preview-token-abuse, preview-exposure, diff-dos.
