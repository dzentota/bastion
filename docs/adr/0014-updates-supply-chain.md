# ADR-0014: Обновления и цепочка поставок (по модели Airship)

- Статус: принято
- Дата: 2026-10-30

## Контекст

Правило 11 манифеста.

## Решение

Только подписанные пакеты из собственного реестра, верификация через Chronicle; зависимости вендорятся; SBOM в релизе; автообновления безопасности по умолчанию; ключ подписи офлайн. Halite для секретов в БД.

## Уточнение: реализация для расширений (2026-10-31)

Модель Gossamer: публичный append-only журнал (Chronicle) с подписанными записями издателей.

- Записи: `key-append`, `key-revoke`, `release` (BLAKE2b-512 архива). Конверт подписан Ed25519 с доменным префиксом `bastion-ledger-v1`.
- Права подписанта (`TrustState`): первый ключ издателя самоподписан; следующие добавляет только активный ключ того же издателя;
  отзывает другой активный ключ или Super Provider; отозванный ключ вернуть нельзя; одна версия — один digest навсегда.
- Ответ Chronicle проверяется закреплённым ключом сервера (`Body-Signature-Ed25519`), записи — хэш-цепочкой
  `BLAKE2b-256(contents, key: prev)`, которая обязана продолжать локальную голову: переписывание, форк и откат отвергаются.
  Формат цепочки — собственный, совместимость с paragonie/chronicle не заявляется.
- Локальная реплика (`?_ledger`) подписана HMAC ключом вне БД.
- Реестр релизов (`latest.json`, `.zip`, `.zip.sig`) недоверенный: ставится только то, что засвидетельствовано журналом.
- Когда канал настроен (`updates.*` в config.json), то же правило действует и для ручной загрузки в админке.
  Ротация ключа издателя разрешена, если новый ключ активен в журнале.
- Отзыв ключа при синхронизации выключает расширения, закреплённые на этом ключе.
- Автообновления: `bin/bastion updates:run` по cron. Издатель: `bin/bastion-ext record …`.
- Без канала — Degraded Mode: только ручная загрузка с закреплённым ключом.
- Не сделано: обновление ядра (оно ставится через Composer с завендоренными зависимостями), SBOM, показ состояния канала в админке.

## Уточнение: SBOM (2026-10-31)

- `bin/sbom generate` пишет CycloneDX 1.5 (`build/sbom.cdx.json`) из `composer.lock`: purl, лицензии, ссылки на VCS и дистрибутив, граф зависимостей.
- Для каждого пакета — SHA-256 его дерева в `vendor/`. Поэтому `bin/sbom verify` на сервере после выкладки находит изменённый, удалённый или лишний вендорный код.
- Пакеты на dev-ветках помечены `bastion:unpinned-branch` (закреплены только коммитом в lock-файле) — риск виден в SBOM.
- Вывод воспроизводим: время из `SOURCE_DATE_EPOCH`, серийный номер выводится из содержимого.
- CI собирает SBOM по runtime-зависимостям (`--no-dev`), сверяет и публикует артефактом.
- Ограничение: хэш дерева проверяет вендорный код против SBOM, но не против upstream (`shasum` в composer.lock обычно пуст). Сам SBOM не подписан — подпись релиза вместе с ним остаётся задачей процесса выпуска (ключ офлайн).
